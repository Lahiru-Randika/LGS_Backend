# LGS Secure Express Backend

Production-oriented starter backend for the **LGS local government spatial services platform**. It matches the frontend concepts already present in the project: five roles (`CITIZEN`, `GOV_WORKER`, `GOV_ADMIN`, `APPROVER`, `SUPERIOR`), municipal requests, assignment, inspections, approvals, building/GIS search, public facilities/bookings, notifications, dashboards, analytics, property/tax isolation, public news, and contact messages.

## Stack

- Node.js 20+
- Express 5 + TypeScript
- MySQL 8 / MySQL 8.4
- `mysql2/promise`
- Zod request validation
- Argon2id password hashing
- Opaque server-side sessions in `HttpOnly` cookies
- Helmet, CORS allowlist, Origin checks, rate limiting
- Pino structured logging with sensitive-field redaction
- Audit logging for privileged and workflow actions
- SQL migrations + bootstrap seed script
- `DATABASE_URL` connection string

## 1. Configure

```bash
cp .env.example .env
```

Set the database with a single connection URL:

```env
DATABASE_URL=mysql://lgs_app:YOUR_URL_ENCODED_PASSWORD@127.0.0.1:3306/lgs
```

If the password contains characters such as `@`, `#`, `!`, `/`, or `:`, URL-encode them.

For a managed database, the same format works:

```env
DATABASE_URL=mysql://USER:PASSWORD@YOUR-MYSQL-HOST:3306/lgs
DB_SSL=true
```

## 2. Install

```bash
npm install
```

## 3. Create DB + migrate + create the first Superior

Update these in `.env` first:

```env
BOOTSTRAP_SUPERIOR_EMAIL=superior@lgs.gov.lk
BOOTSTRAP_SUPERIOR_PASSWORD=USE_A_LONG_RANDOM_PASSWORD
```

Then:

```bash
npm run db:setup
```

That command runs:

```bash
npm run db:create
npm run db:migrate
npm run db:seed
```

If your managed MySQL account is not allowed to create databases, create the database in the provider console and run only:

```bash
npm run db:migrate
npm run db:seed
```

## Authentication model

The backend does **not** trust a role supplied by React.

Public registration always creates a `CITIZEN`. Government accounts are created through a one-time invitation generated by an authorized `SUPERIOR`. Sessions are random opaque tokens; only a SHA-256 hash of each token is stored in MySQL. The browser gets the raw session only in an `HttpOnly` cookie.

The frontend should use:

```text
POST /api/v1/auth/login
GET  /api/v1/auth/me
POST /api/v1/auth/logout
```

and keep `credentials: 'include'` in its API helper.

## Security decisions already implemented

- no role/permission trust from the frontend
- no authentication token in `localStorage`
- `HttpOnly` session cookie
- session revocation on password/access/status changes
- Argon2id password hashing
- login rate limiting and account lockout
- CORS allowlist
- unsafe-method Origin checking
- Helmet security headers
- strict Zod request validation
- parameterized SQL through `mysql2`
- no SQL interpolation for user input
- soft-delete for service requests instead of destructive deletion
- optimistic request versioning (`409` on stale updates)
- immutable request status history
- assignment history
- immutable approval decision records
- citizen/internal note separation
- citizen/internal attachment visibility separation
- file size/count limits
- PNG/JPEG/PDF magic-byte validation
- randomized private filenames
- SHA-256 attachment integrity hashes
- audit logs for sensitive actions
- public building API excludes property/tax information
- tax routes require `tax.read`
- map/GIS proxy targets are fixed server configuration, preventing arbitrary SSRF proxying

See `docs/SECURITY.md` before production deployment.

## Creating requests from the existing frontend

JSON works when there are no files. For image/PDF evidence, send `multipart/form-data`:

- field `payload`: JSON string
- field `files`: up to the configured file count

Example payload:

```json
{
  "clientRequestId": "a4d69ac3-3895-4586-977e-29b2be6f3a65",
  "type": "COMPLAINT",
  "title": "Blocked municipal drain",
  "description": "Water is backing up after rain and reaching the road.",
  "priority": "HIGH",
  "contactPreference": "PORTAL",
  "location": {
    "kind": "POINT",
    "latitude": 6.9105,
    "longitude": 79.8634,
    "label": "Municipal drain beside the main road"
  }
}
```

`clientRequestId` makes submission idempotent: accidental double-submission returns the existing request code rather than creating a second case.

## Production note

This is a strong application baseline, not a claim of government security accreditation. Before real citizen/financial data, follow `docs/SECURITY.md`: managed TLS, secrets manager, MFA/SSO for privileged users, private object storage, database backups/PITR, encryption at rest, centralized logs/SIEM, vulnerability/dependency scanning, WAF/reverse proxy, penetration testing, and jurisdiction-specific privacy/records-retention requirements.
